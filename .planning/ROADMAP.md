# Roadmap: Procurement Intelligence Platform

## Overview

Five phases build the platform in strict dependency order: infrastructure and schema first (because schema mistakes are irreversible), then the scraper pipeline that populates data (because nothing else has value without listings), then the search layer that queries it (because the API contract must be stable before the UI is built), then the web application that delivers it to the BD team, and finally scheduling and hardening that automate and protect it. Each phase delivers a coherent, independently verifiable capability. The BD team starts using the platform daily once Phase 4 ships.

## Phase Details

### Phase 1: Infrastructure
**Goal**: The EC2 instance is live, all services run in Docker Compose, PostgreSQL has the complete schema with all indexes and constraints, and TLS is terminated — ready to receive data.
**Depends on**: Nothing (first phase)
**Requirements**: INFR-01, INFR-02, INFR-03, INFR-04
**Success Criteria** (what must be TRUE):
  1. `docker compose up` on EC2 starts all services (PostgreSQL + pgvector, scraper container, Next.js app, Nginx) without errors
  2. PostgreSQL schema contains all tables (listings, portals, scrape_runs) with HNSW index, tsvector GIN index, TIMESTAMPTZ columns, and (source_portal, source_listing_id) composite unique constraint
  3. Terraform apply provisions EC2 in ca-central-1 — `terraform plan` shows no drift after apply (NOTE: local state, NOT S3 remote state — user override)
  4. HTTPS resolves at procurement.eliastools.com with valid TLS certificate, and HTTP redirects to HTTPS

### Phase 2: Scraper Pipeline
**Goal**: The scraper runs manually against all 63 portals, populates listings into PostgreSQL with valid structured fields and embeddings, and logs per-portal audit data — ready to be queried.
**Depends on**: Phase 1
**Requirements**: SCRP-01, SCRP-02, SCRP-03, SCRP-04, SCRP-05, SCRP-06
**Success Criteria** (what must be TRUE):
  1. Running `python main.py` against all 63 portal configs completes without unhandled exceptions and populates listings in PostgreSQL
  2. A sample of extracted listings contains all required fields (title, description, posting date, closing date, source portal, classification codes, region, contract value, contact info, document links) with no hallucinated values rejected by post-extraction validation
  3. The scrape_runs table shows a per-portal row for every run with success/fail status, listing count, and duration
  4. Re-running the scraper on the same portals upserts existing listings rather than creating duplicates (idempotent on source_portal + source_listing_id)
  5. Every inserted listing has a populated embedding vector generated by text-embedding-3-small stored with model name metadata

### Phase 3: Search Layer
**Goal**: A validated search API supports hybrid keyword + semantic queries with the full filter suite, returning correctly ranked results from real listing data.
**Depends on**: Phase 2
**Requirements**: SRCH-01, SRCH-02, SRCH-03, SRCH-04, SRCH-05, SRCH-06, SRCH-07, SRCH-08, SRCH-09, SRCH-10
**Success Criteria** (what must be TRUE):
  1. A keyword query ("IT consulting") returns listings whose title or description contains the term, ordered by relevance
  2. A natural language query ("construction contracts expiring next month in Ontario") returns semantically relevant listings via pgvector cosine similarity
  3. Hybrid search (combined keyword + semantic via Reciprocal Rank Fusion) returns results that satisfy 20 real procurement queries validated with the BD team
  4. All six filter dimensions work correctly in combination: closing date range, region/province, source portal, posting date range, category/commodity code (NAICS/UNSPSC/GSIN), and estimated contract value range
  5. Results can be sorted by posting date, closing date, relevance score, and contract value; default view shows only open/future listings

### Phase 4: Web Application
**Goal**: The BD team can log in, search all 63 portals from one dashboard, view listing details, and monitor scraper health — the platform is usable for daily work.
**Depends on**: Phase 3
**Requirements**: DASH-01, DASH-02, DASH-03, DASH-04, DASH-05, DASH-06, DASH-07, DASH-08, DASH-09
**Success Criteria** (what must be TRUE):
  1. A user can log in with username and password, browse paginated listing results, apply filters, and stay authenticated across browser sessions
  2. Clicking a listing opens a detail view showing all extracted fields, document attachment links, contact information, and a direct link to the original source portal page
  3. Listings posted since the user's last visit are visibly badged as "New" on the results list
  4. The current search and filter state is encoded in the URL so a user can share a filtered search via link and the recipient sees the same results
  5. A scraper health page shows each portal's last-run date, success/fail status, and listing count, and the dashboard displays a data freshness indicator showing when listings were last updated

### Phase 5: Scheduling and Hardening
**Goal**: The scraper runs automatically every night at 2 AM ET, monitoring alerts fire if anything goes wrong, and Docker Compose is hardened for production — the platform operates reliably without manual intervention.
**Depends on**: Phase 4
**Requirements**: INFR-05
**Success Criteria** (what must be TRUE):
  1. The scraper pipeline triggers automatically at 2 AM ET nightly without manual intervention, and new listings appear in the dashboard the following morning
  2. A CloudWatch alarm fires if no new listings have appeared in 26+ hours (dead-man alert), and a second alarm fires if EC2 memory exceeds 80%
  3. A per-portal yield alert fires when a portal that previously returned listings returns 0 listings on a run
  4. Docker Compose uses pinned image digests, restart: always policies, log rotation, and a separate docker-compose.prod.yml — the stack recovers from EC2 reboots automatically
